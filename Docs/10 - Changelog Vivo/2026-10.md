## 2026-10-01 — Estabilidade: tela não cai mais com "Application error: a client-side exception"

**Área(s):** shell de todas as telas autenticadas · escopo de loja · escopo de período operacional
**Persona afetada:** todas (Loja, Gestor de Fábrica, Chão de Fábrica, Gestor de Dados, Administrador, Master)
**Origem:** relato do cliente — tela branca "Application error: a client-side exception has occurred while loading …netlify.app", de forma intermitente.

**O que mudou (humano):**
- Se o navegador bloquear o armazenamento do site (Safari com cookies bloqueados, navegador embutido de app, modo restrito), as telas **continuam abrindo**. Antes, `/loja` e `/loja/pedidos` caíam por inteiro.
- Se algo ainda quebrar numa tela, aparece uma tela de recuperação com **Tentar novamente / Recarregar a página** e um código para o suporte, em vez da tela branca genérica do Next.
- Depois de uma nova publicação, abas antigas que perderam arquivos recarregam sozinhas **uma vez** (com trava anti-loop).

**Onde mudou (técnico):**
- `src/lib/safe-storage.ts` (novo) — `safeStorageGet/Set` com try/catch; o próprio acesso a `window.localStorage` pode lançar `SecurityError`.
- `src/lib/use-store-scope.ts`, `src/lib/use-operational-date-scope.ts` — trocam `window.localStorage` direto (lido **durante o render**) por `safeStorage*`; `history.replaceState` protegido.
- `src/app/error.tsx`, `src/app/global-error.tsx`, `src/components/shared/error-fallback.tsx` (novos) — antes não existia nenhuma error boundary no app.
- `src/lib/chunk-error-recovery.ts` (novo) — detecta `ChunkLoadError` e recarrega uma vez por 60 s.
- Testes: `safe-storage.test.ts`, `chunk-error-recovery.test.ts`.

**Por que mudou:**
> Reproduzido em navegador real contra a produção: com o storage bloqueado, `/loja` e `/loja/pedidos` lançavam `SecurityError` no render e derrubavam a página. Sem `error.tsx`/`global-error.tsx`, qualquer exceção de cliente virava a tela genérica do Next. Com a correção: 25 rotas abertas com storage bloqueado, 0 falhas.

**Risco residual / TODO:**
- [ ] A causa exata do episódio do cliente não foi capturada (não há console do aparelho dele). Esta é a causa **reproduzida**; se voltar a ocorrer, o código exibido na tela de recuperação aponta a origem.
- [ ] Os hooks de dados (`use-master-data`, `use-factory-planning`, etc.) assumem que a API devolve o formato esperado. Resposta 200 com corpo vazio/`null` derruba a tela (agora cai na tela de recuperação, não mais na genérica). Validar o formato nos hooks é uma evolução à parte.
- [ ] `/administrador/usuarios` em modo leitura do Master gera o erro de hidratação React #418 (`readClientAccessContext()` lido no render). A página se recupera sozinha; não corrigido aqui.
